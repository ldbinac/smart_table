# 多维表格大数据量（千条+）性能分析与优化方案

> 日期：2026-10-23
> 背景：数据量上千条后，打开表格、编辑单元格、滚动、搜索均出现明显卡顿。
> 方法：前后端代码链路逐点排查 + 对照飞书多维表格 / WPS 多维表格 / SeaTable / Teable / Airtable / Grist / APITable 的公开架构方案。
> 结论先行：**渲染层不是瓶颈（VTable Canvas 虚拟滚动已就位），瓶颈在「后端逐记录读时计算」与「前端全量进内存 + 全量重算」的数据供给层。**

---

## 〇、结论摘要（TL;DR）

| 层 | 一句话根因 | 最严重的位置 |
|---|---|---|
| 后端 | `GET /tables/{id}/records` 在**循环内**逐记录做 lookup / 公式计算，每条记录触发 **3~7 条 SQL + 1 次源表全表物化** | `routes/records.py:169-176` → `lookup_service.py:962-974` |
| 前端 | 任意一条记录变化都触发 **deep watch → 清全量缓存 → 全量重转换 → VTable 全量销毁重建**，单次编辑 O(N)，流式加载 O(N²) | `VTableView.vue:6847-6905` → `6541-6631` |

**复杂度模型**（N = 每页记录数，L = lookup 字段数，S = 源表行数）：

```
后端单次列表请求 SQL 数  ≈  N × (1 + 6L)   +   2·N·L 次源表全表扫描（共 N·L·S 行 I/O）
per_page=200, L=1, S=1000  →  1400 条 SQL + 200 万行读取  →  必然秒级超时
```

```
前端首屏加载（流式 200/页，共 M 页）：
  总代价 ≈ Σ(i=1..M) [ transformRecords(i×200 × F) + buildTableConfig + new ListTable + 重绑 15 个事件 ]
  1000 条 = 5 页  →  5 次全量重建，O(N²/页大小)
```

> 一句话：**不是数据库慢，是 N+1 慢；不是 Canvas 慢，是全量重算慢。**

## 一、当前架构与数据链路

### 1.1 技术栈

| 层 | 选型 | 关键证据 |
|---|---|---|
| 前端框架 | Vue 3 + Pinia + Vite | `smart-table/src/stores/tableStore.ts` |
| 表格渲染 | **@visactor/vtable 1.26（Canvas，自带虚拟滚动）** | `smart-table/package.json:22`，`Base.vue:152` `useVTable = ref(true)` |
| 本地缓存 | Dexie / IndexedDB | `recordService.getLocalRecordsByTable` |
| 后端框架 | **Flask 3.0（同步阻塞，全仓 0 处 async）** | `requirements.txt:2` |
| ORM | SQLAlchemy 2.0 + Flask-SQLAlchemy 3.1 | `requirements.txt:5-6` |
| 数据库 | 默认 SQLite，生产 PostgreSQL | `app/config.py:78 / 108-111` |
| 缓存 | Flask-Caching RedisCache（TTL 300s） | `app/config.py:152-154` |
| 序列化 | marshmallow + 手写 `to_dict()` | `app/models/record.py:142` |

### 1.2 读链路（打开一个表）

```
Base.vue 挂载
  → tableStore.selectTable(tableId)
  → recordService.streamLoadRecords(每页 200，流式追加)
       每页 onProgress: records.value = [...records.value, ...newRecords]   ← O(N²) 拷贝
       onComplete 后:  refreshRecords() 从 IndexedDB 全量回读并整体替换      ← 又一次全量
  → Base.vue filteredRecords = applyFilters + applySorts(全量浅拷贝)         ← 第 1 次全量排序
  → VTableView sortedRecords = [...records].sort(...)                       ← 第 2 次全量排序
  → transformRecords(全量)：逐行 × 逐字段 switch + 公式兜底 + 成员解析       ← O(N×F)
  → SmartTableDataSource.updateMemoryCache(tableRecords, 0)                 ← 一次性灌满，懒加载失效
  → VTable CachedDataSource → Canvas 虚拟滚动渲染
```

后端：

```
GET /api/tables/{id}/records?page=&per_page=
  → 权限校验（2-3 条 SQL，请求级一次，OK）
  → RecordService.get_table_records：count() + offset/limit（缺 is_deleted 过滤）
  → LinkService.batch_get_record_link_ids（✅ 已批量化，仅 2 条 SQL）
  → 预查 formula_fields / lookup_fields / table_context（✅ 已预取）
  → for record in records:                       ← 🔴 循环内 N+1 开始
       record.to_dict()
       FormulaService.compute_record_formulas()   → 每条记录 1 次 Field 查询 + lookup 再算一遍
       LookupService.compute_lookup_value()       → 每条记录 3 条 SQL + 源表全表扫描
  → jsonify 全量响应
```

### 1.3 写链路（编辑一个单元格）

```
VTable 编辑完成 → recordService.updateRecord(API)
  → tableStore.updateRecord：records.value[index] = {...}
  → 🔴 watch(() => tableStore.records, { deep: true })
  → await nextTick()
  → 🔴 clearTransformCache()   清掉全部行缓存
  → 行数没变 → preloadMemberUsers()（全表 × MEMBER 字段遍历，再 clearTransformCache）
  → updateTableData() → clearCache() + updateMemoryCache(全量) + renderWithRecreateCells()
```

## 二、后端性能瓶颈清单

### 🔴 P0-1 · Lookup 字段 N+1 + 源表全表扫描（第一元凶）

- **位置**：`app/routes/records.py:169-176`（`for record in records` 循环内）

```python
169  if lookup_fields:
170      for lookup_field in lookup_fields:
172          item['values'][str(lookup_field.id)] = LookupService.compute_lookup_value(record, lookup_field)
```

- **实现**：`app/services/lookup_service.py:962-974` —— **每次调用**都执行：

```python
963  source_records = Record.query.filter_by(table_id=str(source_table_id), is_deleted=False).all()   # 源表全量
968  source_fields = Field.query.filter_by(table_id=str(source_table_id)).all()                       # 源表字段
973  current_fields = Field.query.filter_by(table_id=str(record.table_id)).all()                      # 当前表字段
```

- **影响**：每条记录 × 每个 lookup 字段 = 3 条 SQL + 1 次源表全表物化。`per_page=200`、1 个 lookup 字段 → **600 条 SQL + 200 次源表全表扫描**；源表 1000 行时单次请求读 20 万行。
- **放大**：`Record` 模型 `lazy='joined'` 强制 3 个 JOIN（`models/record.py:86/92/98`），那 200 次全表扫描每次还额外 join `tables` + 2× `users`。

### 🔴 P0-2 · 公式上下文里的**嵌套** Lookup N+1（同一值被算两遍）

- **位置**：`app/services/formula_service.py:1860-1865`

```python
1860  for f in all_fields:
1861      if f.type == FieldType.LOOKUP.value:
1863          context[f.name] = LookupService.compute_lookup_value(record, f)   # 又一层 N+1
```

- **影响**：只要表里**同时存在公式字段和查找字段**，每个 lookup 值就被算 **2 次**（`records.py:172` 一次、`_build_formula_context` 一次），SQL 数直接翻倍成 `N × (1 + 6L)`。

### 🔴 P0-3 · `compute_record_formulas` 每条记录重查一次全表字段

- **位置**：`app/services/formula_service.py:1930-1933`

```python
1932  all_fields = Field.query.filter_by(table_id=table_id).all()      # ← 每条记录 1 次 DB
1933  context_by_name = cls._build_formula_context(all_fields, values, record=record)
```

- 调用方 `records.py:130` **已经查出过** `formula_fields`，但 `all_fields` 漏了预取 → 200 条记录 = 200 次 `SELECT * FROM fields`。

### 🔴 P0-4 · 搜索：全表加载后在 Python 里切片

- **位置**：`app/services/record_service.py:908-928` + `routes/records.py:104-111`

```python
918  for field_id in valid_field_ids:
923      conditions.append(Record.values.op('->>')(field_id).ilike(like_pattern))   # 每字段一个 ILIKE
927  results = query_obj.all()        # ← 无 limit，全量物化
```
```python
106  records = RecordService.search_records(table_id, search)
107  total = len(records)              # Python 侧计数
109  records = records[start:end]      # Python 侧切片
```

- JSON 列内取值无法走索引 → 必然全表扫描；20 个字段 = 20 个 OR 条件；1000 条全部 load 成 ORM 对象只为返回 20 条。
- 同类：`routes/records.py:1889-1905`（`search_linkable_records`）、`routes/open_api.py:186-199`（**OpenAPI 搜索完全无分页**）、`link_service.py:712/1847-1880`、`record_service.py:736/797`（树形记录）。

### 🟠 P1-1 · 公式引擎：每行重新 parse + 每行 md5(json.dumps(context))

- `formula_service.py:1636-1649`：AST **无缓存**（`lru_cache` 在 `:21` 被 import 却未使用），每条记录重新 tokenize + 递归下降解析。
- `formula_service.py:2254-2262`：缓存 key 需把**整份 context** `json.dumps` + md5，每行每公式一次。
- 缓存存的是**计算结果**（依赖全行数据）→ 命中率极低，反而多付 2 次 Redis 往返。
- `has_column_ref` 为真时**完全禁用缓存**（`:1634`）→ 整列引用公式每行必全量求值。
- 整列上下文缓存 TTL 仅 **10 秒**（`:1604`），高频请求下反复重建全表快照；`_build_columns` 是 O(记录数 × 字段数) 双层 Python 循环（`:1803-1807`）。

### 🟠 P1-2 · 主查询本身的问题

- `record_service.py:200-204`：`Record.query.filter_by(table_id=table_id)` **缺 `is_deleted=False`** → 软删除记录也被查出并序列化，数据越攒越慢（对比 `formula_service.py:1788` 是带该过滤的，不一致）。
- `count()` 每页独立执行；`OFFSET` 深分页线性变慢；无游标分页。
- `models/record.py:86/92/98`：`table / creator / updator` 全部 `lazy='joined'` → 每次 `Record.query` 强制 `LEFT OUTER JOIN tables + 2× LEFT OUTER JOIN users`。

### 🟠 P1-3 · 字段元数据**零缓存**

| 缓存对象 | 状态 |
|---|---|
| 系统配置 | ✅ Redis 24h（`config_cache_service.py:52-97`） |
| 公式整列上下文 | ⚠️ 进程内 dict，TTL 10s |
| 公式计算结果 | ⚠️ Redis 300s，key 含全行 context，命中率低 |
| **Field 元数据** | ❌ **无缓存**，每次 `Field.query.filter_by(...).all()` |
| **View / Table** | ❌ 无缓存 |

`records.py` 内**重复查了 3 次字段**（`:119` link + `:120` link + `:130` formula + `:141` lookup）。

### 🟡 P2 · 写路径与其他

- `routes/records.py:643-660` `batch_update_records`、`:784-801` `batch_delete_records`：**逐条循环**（SELECT + 权限 + UPDATE + history INSERT），1000 条 ≈ 3000+ SQL。对比批量**创建**（`:405-412`）已用 `executemany`，明显不对称。
- `record_service.py:123-157` 自动编号：Redis 不可用回退时，**每条记录一次全表扫描 + Python 正则**，批量创建 1000 条 = 1000 次全表扫描。
- `app/config.py:236` 开发环境 `SQLALCHEMY_ECHO = True` → 每条 SQL 走 logging，dev 慢一个数量级。
- 全仓**无流式响应**，全部 `jsonify()`；`dashboards_share.py:338` 硬编码 `.limit(1000).all()`。
- **分组/聚合不在后端**：`group_bys` 只是视图配置里的 JSON（`routes/views.py:49,67`），聚合在前端算 → 前端必须拉全量数据，间接放大列表接口压力。

## 三、前端性能瓶颈清单

### 🔴 P0-5 · `deep: true` watch + 无条件清全量缓存 → 单次编辑 O(N)

- **位置**：`smart-table/src/components/views/TableView/VTableView.vue:6847-6905`

```ts
6847  watch(() => tableStore.records, async () => {
6856    await nextTick();
6867    clearTransformCache();                 // ← 无条件清空全部行转换缓存
6876    const prevTotal = smartDataSource.totalCount;
6882    if (expectedTotal !== prevTotal) {
6887      updateTable();                       // ← 行数变化：全量销毁重建
6900    } else {
6902      preloadMemberUsers();
6903      updateTableData();                   // ← 行数不变：清缓存 + 全量重灌 + 重绘
6905  }, { deep: true });
```

- `{ deep: true }` 对 1000+ 行 × 全字段做**深度依赖收集**，是 O(N×F) 的固定开销。
- `updateTable()`（`:6541-6631`）代价：

```ts
6552    ensureLinkGroupNames();             // 无条件发起关联组名请求
6568    (tableInstance as any).release();
6575    tableContainerRef.value.innerHTML = '';
6592    const config = buildTableConfig();  // 全量 transformRecords + 列配置 + customRender/customLayout 重建
6593    tableInstance = new ListTable(tableContainerRef.value, config);
6594    bindTableEvents();                  // 重新绑定 ~15 个 VTable 事件
```

- `updateTableData()`（`:6637`）名为"增量"，实为 `clearCache()` + `updateMemoryCache(全量)` + `renderWithRecreateCells()`。
- 另：`VTableView.vue:6965-6969` 监听 `userCacheStore.cacheStats.size`，成员名逐个加载完成时会**反复**触发全量清缓存 + 重转换，首屏期间集中爆发。

### 🔴 P0-6 · 流式加载每页触发表格全量重建 → O(N²)

- `stores/tableStore.ts:104-106`：每页到达执行 `records.value = [...records.value, ...newRecords]`（新数组引用 + 长度变化）。
- 配合 P0-5 的 `expectedTotal !== prevTotal` 判定 → 每页一次 `updateTable()` 全量重建。1000 条 = 5 页 = 5 次「全量转换 + VTable 重建」。
- `tableStore.ts:108-112`：`onComplete` 后再调 `refreshRecords()` 从 IndexedDB **全量回读**并整体替换 → 再触发一轮 deep watch + 全量重建。

### 🔴 P0-7 · `SmartTableDataSource` 的懒加载形同虚设

- `services/SmartTableDataSource.ts` 设计了 CachedDataSource + LRU 按需取数，**但调用方一次性灌满**：

```ts
5412    smartDataSource.updateMemoryCache(tableRecords, 0);   // ← 全量写入
5413    smartDataSource.markFullyLoaded();
```

- 且 `transformRecords(sortedRecords.value)`（`:5356`）在灌缓存**之前**已经全量转换完毕。
- 结论：**虚拟滚动只省了 Canvas 绘制，没省数据准备**。1000 条全部进内存、全部被 Vue Proxy 包裹。
- `updateMemoryCache` 内部 `remaining.slice()` 循环切分（`SmartTableDataSource.ts:124-152`）本身也有 O(N) 多余拷贝。

### 🟠 P1-4 · 双层排序 + `localeCompare`

- `views/Base.vue:342-361` `filteredRecords`：`[...records]` 全量浅拷贝 + `applyFilters` + `applySorts`（第 1 次排序）。
- `VTableView.vue:3161-3202` `sortedRecords`：`[...records.value].sort(...)`（第 2 次排序）—— **同一份数据排两遍**。
- `VTableView.vue:3193` / `utils/sort.ts:129`：比较器内 `String(aVal).localeCompare(String(bVal))`，**未复用 `Intl.Collator`**，N·log₂N ≈ 10,000 次比较 → 数百毫秒级。
- `utils/sort.ts:16`：比较器内 `fields.find((f) => f.id === sort.fieldId)` → 每次比较 O(F) 线性查找，总 O(N·logN·F)。
- `utils/filter.ts:949-957`：`applyFilters` 对**每条记录** `map` 分配一个新数组。

### 🟠 P1-5 · `ref<RecordEntity[]>` 深层响应式

- `stores/tableStore.ts:46` `const records = ref<RecordEntity[]>([])`
- `ref([])` 对数组是**深层响应式** → 1000 条记录 × 每条 `values` 对象全部递归 Proxy 化。`transformRecords` 中 `record.values[field.id]`（`:3441`）每次读取都穿过 Proxy getter，1000×20 = 2 万次代理拦截。
- 项目内**无** `v-memo`、对 records 无 `shallowRef`/`markRaw`。
- `tableStore.ts:428-432 / 732-736`：删除字段时 `records.value.map(...)` 全表重建。

### 🟠 P1-6 · 全表遍历型预处理

- `VTableView.vue:6804-6843` `preloadMemberUsers()`：`tableStore.records` × 全部 MEMBER 字段全量遍历 + `JSON.parse`，末尾再 `clearTransformCache()`。
- `VTableView.vue:7124-7211` `loadLinkDisplayData()`：全表 LINK 字段批量请求（100/批），结束后 `renderWithRecreateCells()` 全量重绘。
- `VTableView.vue:3841-3876` `ensureLinkGroupNames()`：每个 LINK 分组字段发一次请求，且在 `updateTable()` 开头**无条件调用**（`:6552`）。

### 🟠 P1-7 · 分组 / 树形视图强制走 `records` 全量模式

```ts
5418    ...(isTreeView.value ? { records: tableRecords }
5420      : (isGrouped ? { records: tableRecords }
5422        : { dataSource: smartDataSource!.dataSource })),
```

分组与树形视图下 VTable 使用 `records` 数组模式 → **懒加载完全失效**，全量进 VTable。
另：`utils/group.ts:35-128` 分组递归 + 每个分组节点 `calculateAggregations`（**聚合在前端**，每节点遍历该组全部记录）。

### 🟡 P2 · 其他

- `VTableView.vue:6244-6255`：VTable `scroll` 回调内 `getBoundingClientRect` / `getCellRect` → **强制同步回流**，无 throttle / rAF 合并。
- `VTableView.vue:6991-6997`：`window resize` 无节流；`window scroll` 用 `capture=true` 且非 passive（项目已有 `utils/debounce.ts` 但未用）。
- `VTableView.vue:4763-4856 / 4868-4872`：复杂类型列**同时**挂 `customRender`（拼 HTML 字符串）与 `customLayout`（VRender 逐图元构造），滚动时每帧对可见单元格执行字符串拼接 + Group 构造。
- legacy 全量 DOM 路径 `TableView.vue:898-973` / `GroupedTableView.vue:1236`：零虚拟滚动，1000×20 = 2 万个 `TableCell` 实例。当前被 `Base.vue:152` 硬编码开关关掉，但代码仍在维护。
- `components/views/TableView/TableCell.vue:148-151`：每个公式单元格 `JSON.stringify(props.record.values)`；`:176` 每个公式单元格 `console.log`。
- `TableCell.vue:82-121` `loadLinkedRecords()`：N 行 × M 个关联列 = N×M 个 HTTP 请求（legacy 路径）。
- 响应体无字段裁剪：200 条 × 全字段 `values` + `computed_values`。

## 四、业界方案对照

### 4.1 对照表

| 产品 | 存储 / 计算 | 数据加载 | 前端渲染 | 可借鉴点 |
|---|---|---|---|---|
| **飞书多维表格** | 公式**服务端计算**，单表百万热行 | 增量同步 + 只传视口 | 自研 Canvas | 「浏览器只渲染，计算上服务端」；计算下推是分水岭 |
| **WPS 多维表格** | 云端文档模型，服务端筛选/排序/聚合 | 分片拉取 + 本地快照 | Canvas 虚拟滚动 | 视图配置即查询计划，服务端出结果集 |
| **SeaTable**（开源） | 热数据内存 + 操作日志；**大数据后端归档 SQL** | **Big Data View 默认仅载 1000 行，滚动按需取** | 虚拟滚动 | **冷热分层**；大表默认只载窗口 |
| **Teable**（开源） | **一表一真实 Postgres 物理表**，字段即真实列 | **keyset 游标分页**，筛选排序下推 SQL + GIN 索引 | 虚拟滚动 | SQL 直存 + 服务端筛选最省力 |
| **Grist**（开源） | UserAction → DocAction，公式**依赖图增量重算** | WebSocket 推 patch | 虚拟滚动 | 一切变更是 patch；**增量重算** |
| **APITable** | nest-server + room-server（双 WS）+ OT + Redis | 增量 patch | **Canvas 渲染 10 万+ 行** | WS 只推增量 patch，绝不全量刷新 |
| **Airtable** | 全表数据进浏览器 | offset 分页（pageSize ≤ 100） | DOM 虚拟化 | ⚠️ **反面教材**：社区确认 5 万行即卡 |
| **AG Grid / Glide** | — | Viewport / Infinite 懒加载 | Canvas 按需绘制 | 数据源按视口分页供给 |

### 4.2 业界共同设计（五条）

1. **虚拟滚动是标配** —— 我们已有（VTable Canvas），✅ 无需重做。
2. **服务端计算 + 服务端筛选/排序 + 游标分页** —— 这是千条到万条的分水岭，我们**完全缺失**（筛选/排序/分组全在前端）。
3. **变更走增量 patch，永不全量刷新** —— 我们恰好相反：任何变更都全量重建。
4. **公式按依赖增量重算 / 写时物化** —— 我们是**读时逐条重算**。
5. **超大数据冷热分层** —— 我们无分层，全表一视同仁进浏览器。

### 4.3 我们的差距定位

```
                    渲染层 ✅ 已达标（Canvas 虚拟滚动）
                       ↓
        数据供给层 ❌ 全量进内存 + 全量重算  ← 卡顿主因（前端）
                       ↓
        计算层     ❌ 读时逐记录计算 + N+1    ← 卡顿主因（后端）
                       ↓
        存储层     ⚠️ values JSON 列，无法索引化筛选排序
```

**缺的不是渲染层，是「服务端计算下推」与「增量更新」这两个架构能力。**

### 5.2 P1 架构级（对齐飞书 / Teable，支撑数万条）

#### P1-1 · 筛选 / 排序 / 搜索 / 分组全面下推服务端

`GET /api/tables/{id}/records` 增加 `filters`、`sorts`、`search`、`group_by`、`cursor` 参数：

| 数据库 | 方案 |
|---|---|
| SQLite | JSON1 表达式 `json_extract(values,'$.fid')` + **表达式索引**；搜索接 **FTS5** 虚拟表（写入时同步维护） |
| PostgreSQL | `jsonb` + **GIN (`jsonb_path_ops`)** 索引 + 表达式索引；搜索用 `pg_trgm` + GIN |

- 分组与聚合（`COUNT/SUM/AVG/MIN/MAX`）在 SQL 层完成，前端只接收分组树 + 聚合值。
- 前端 IndexedDB 降级为**离线兜底**，不再作为主数据源参与全量计算。

#### P1-2 · offset 分页 → keyset 游标分页

- 以 `(created_at, id)` 或当前排序键做游标（对齐 Teable `nextCursor`）。
- `total` 不再每页 `count()`：改用写路径维护的 `tables.record_count` 返回估算值。

#### P1-3 · 公式 / lookup 改写时计算 + 物化（核心架构升级）

- 记录 create / update 时在**写路径**计算公式与 lookup 值，物化进 `record.computed_values`（JSON 列）。
- 依赖失效：字段配置变更、被引用表写入时，按依赖关系批量置脏 + 后台任务重算（先做**表级**粗粒度，再做**列级**，借鉴 Grist 依赖图思想）。
- `get_records` 读路径退化为纯 SQL 读取 + 序列化，O(1)。
- WebSocket 广播 `data:record_updated` 补带 `computed_values` diff，前端免兜底重算。

#### P1-4 · 前端数据层脱离响应式

- `records` 改 `shallowRef` + 显式版本号（F1 的完成态）。
- 进一步：行数据用 `markRaw` 存于非响应式 Map，仅"渲染结果 + 版本号"走 ref，对齐「数据层不可变 + 渲染层最小订阅」。

#### P1-5 · 字段投影（按需返回列）

视图只请求**可见列**的 values，隐藏列不传输、不转换。1000 行 × 20 列中若只显示 8 列，传输与转换量降 60%。
